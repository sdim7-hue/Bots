# Архитектура Bots

> Адаптировано из референс-системы Ильи (оркестрация Claude Code). Механика Ильи
> (tmux/SSH/серверы NVR) — его среда; у нас целевая tmux-схема появится после переезда
> на Ubuntu. Сейчас ядро OS-агностично.

## Участники

```
Человек → Claude-оркестратор → боты Claude Code → GitHub
```

- **Человек** — цель, приоритеты, подтверждение необратимых действий.
- **Claude-оркестратор** — код не пишет; формулирует брифы, контролирует, ведёт документацию.
- **Боты Claude Code** — пишут код, ревьюят, делают discovery.
- **GitHub** — нейтральный слой: Issues (очередь задач), Actions (автоконтроль), репозиторий (код).

## Роли ботов (конфигурация N+1)

- **Диспетчер** — раздаёт задачи, забирает диффы, отправляет на ревью, эскалирует. Код не пишет.
- **Кодер 1..N** — пишут код по брифу. Один коммит на задачу. Push сами не делают (делает оркестратор).
- **Ultra Reviewer** — read-only. Вердикт по каждому коммиту: 🟢 GREEN / 🟡 YELLOW (+followup) / 🔴 RED (блокер).

На старте — минимум (1 кодер + ревьюер + диспетчер). Масштабирование позже.

## Режимы работы

1. **Ручная оркестрация** — оркестратор формулирует каждый бриф, контролирует каждый шаг.
   Для точечных и нестандартных задач.
2. **Автономный цикл** — диспетчер получает одну задачу и сам гоняет кодера ↔ ревьюера до
   результата; человек включается на решениях и подтверждениях.

## Очередь задач — GitHub Issues

Задача = issue с меткой статуса:
`queued` → `in-progress` → `review` → `done` (или `failed`).
Оркестратор читает очередь по метке, ведёт состояние, контролирует переходы.

## Структура брифа боту (5 блоков — обязательно)

1. **Контекст / зачем** — смысловая цель задачи, не техническая.
2. **Конкретные действия** — чёткие шаги (с примерами команд, если применимо).
3. **Формат результата** — где и в каком виде положить результат.
4. **Ограничения** — что НЕ делать (scope, read-only, не трогать X).
5. **После выполнения** — что дальше (idle / следующая задача / эскалация).

Бриф = направление + критерий успеха, не пошаговая инструкция написания кода.
Узкие рамки — только для архитектурных/политических решений или по явному указанию.

## Эскалации (типы)

- **A — запрос данных** у человека (креды, реквизиты, конфиги).
- **B — approval необратимого действия** (деплой, миграция).
- **C — диспетчер решает сам** (техническое, без политики/необратимости) + veto-окно.
- **D — veto оркестратора** (бот нарушил принцип).
- **E — конструктивная критика инструкции** (бот отказался выполнять неверное, с фактами). Самый ценный паттерн.
- **F — discovery-находка** (часть задачи уже сделана / план устарел).

## Адаптер запуска ботов

Интерфейс «запустить бота / отдать бриф / снять результат» абстрагирован.
- **Windows (сейчас):** минимальный вариант (отдельные процессы/окна).
- **Ubuntu (цель):** tmux-панели, автономный цикл — как у Ильи.
Ядро оркестратора при смене ОС не переписывается.

## Граница записи бота — три слоя (14.09.2026)

Флаги разрешений Claude Code (`--disallowedTools`, `--permission-mode`) границей НЕ являются:
подключённые MCP-инструменты их обходят. Поэтому бот работает с
`--permission-mode bypassPermissions`, а защита — механическая:

1. **gate-clone** (`scripts/bot-run.sh`) — изолированный чекаут без `remote` и с пустым
   `credential.helper`: запушить нельзя. Проверяется в предполёте и повторно после
   подготовки гейта.
2. **ОС-песочница** (`scripts/sandbox-run.sh`, bubblewrap) — хост виден read-only, на запись
   только гейт, `/tmp` (tmpfs) и состояние CLI (`~/.claude`, `~/.claude.json`,
   `~/.cache/claude-cli-nodejs`). Свои pid/uts/ipc namespace, `--die-with-parent`.
   Сеть НЕ отрезается: без неё бот не дойдёт до API. Запрещена не работа с внешним
   миром, а бесконтрольная ЛОКАЛЬНАЯ ЗАПИСЬ — это разные ворота.
3. **cgroup-лимиты** через `systemd-run --user --scope`: `MemoryMax` (4G), `CPUQuota` (200%),
   `TasksMax` (512). Это гигиена ресурсов, не безопасность: при недоступной шине
   systemd --user прогон продолжается с предупреждением, потому что граница — в bwrap.

Граница **доказывается пробой** в предполёте (проверка 9), а не наличием bwrap: запись в
гейт разрешена, запись в `$HOME` и запись через symlink из гейта наружу — запрещены.
Любой из трёх исходов не тот — прогон не стартует.

### ⚠ Оркестратор запускается НЕ из гейта

`scripts/bot-run.sh` делает `cd "$BOTS_DIR"` (не `cd "$GATE"`) и передаёт каталог бота
через `BOTS_CHECKOUT`. Причина: при `python -m` в `sys.path[0]` попадает cwd, а гейт —
клон этого же репозитория, поэтому его копия `orchestrator/` перекрывала настоящую.
Два последствия: правки раннера не применялись, и бот, имеющий запись в гейт, мог
подменить код оркестратора для следующего прогона — то есть выполнить код ВНЕ песочницы.
Дополнительно запуск идёт с `python3 -P` (cwd не добавляется в `sys.path`).
