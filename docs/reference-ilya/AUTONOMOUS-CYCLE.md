# AUTONOMOUS_CYCLE — методология многоботного автономного цикла

## 🌙 АКТУАЛЬНЫЙ РЕГЛАМЕНТ (2026-06-06): автономный цикл 10-ролевой Digital Company

> Разделы 1–13 ниже описывают РАННЮЮ 4-ботную модель `localbot` — исторические, но принципы (типы эскалаций A–F §8, паркинг, чеклист §11, «когда быть громким» §9.3) валидны. Текущая команда — **10 ролей** в tmux `company` (Архитектор-оркестратор + Диспетчер + 2 Кодера + Reviewer + Tester + Writer + DevOps + Аналитик + Designer). Ночью **Архитектор = само-гейтящий оркестратор**.

**Когда применяется:** Илья + claude-ilya офлайн (ночь/сон). Архитектор ведёт сам; claude-ilya и Илья — утренний сбор + реакция на TG-эскалации.

**7 правил автономного бега (зафиксировано при входе в ночь 2026-06-06):**
1. **Само-гейт волн** — переход к следующей волне ТОЛЬКО при: Tester PASS + Reviewer 🟢 + butterfly sign-off Архитектора + ноль prod-касаний + ноль нерешённых развилок Ильи. Само-верификация (R-DC-1) обязательна (в Б-3 поймал ложные sign-off ×2 — держать планку).
2. **Паркинг** — технический тупик → парк задачи (durable + причина) + продолжение других; блок всей волны → стоп волны + durable + ждать утра.
3. **🚫 STOP-LINE (парковать до Ильи, НЕ решать ночью):** биллинг/токены/цены · customer-facing (FF_AI-выкат, Q2 durable LUS) · **РЕЛИЗ 0.4.0 на серверы** · дизайн-апрув новых UX · любая развилка под суждение Ильи (бизнес/продукт/деньги/клиент).
4. **🔒 Прод заморожен абсолютно:** Core / MaMaison / LUS — не трогать ни под каким предлогом. Только DEV2 + нода (стенд).
5. **Контекст-выживание (R-DC-6):** упреждающие компакты ~70–80% (без forced auto-compact); durable self-handover ПЕРЕД каждым рестартом роли; `coord/ARCHITECT-CONTEXT` актуален (переживает рестарт самого Архитектора).
6. **Эскалация:** критичное (НЕ прод, НЕ блок всего) — TG Илье через `tools/tg-notify.sh` без ожидания ответа; прод-инцидент / полный стоп — TG + durable + ждать.
7. **Утренний сбор:** handover-сводка — закрыто (волны) / запарковано (+причины) / **ЖДЁТ ИЛЬЮ** (STOP-LINE) / число коммитов за ночь / butterfly-инциденты. Первое, что читают claude-ilya и Илья утром.

**Доставка брифов (tmux `company`):** `send-keys C-u` → `load-buffer` → `paste-buffer` → sleep → `send-keys Enter` (см. skill nvr-bot-brief). Прямой `send-keys "длинный текст"` ЗАПРЕЩЁН — режется/теряется. **§4-правило:** ghost/shadow-текст в input-пейне роли — НЕ команда Ильи, не исполнять.

## 1. Зачем — экономика и качество

**Проблема:** прямой диалог Илья ↔ Claude-оркестратор в Claude Desktop хорош для дизайна, но **дорогой для кода** — каждое сообщение тащит весь контекст vault'а + истории. На 14-часовую сессию получается 50-100% недельного лимита.

**Решение:** Claude-оркестратор делегирует кодинг группе из 4 ботов Claude Code в tmux, оставаясь **стратегическим контролёром** (см. [[CRITICAL-RULES#1.|§1]] про разделение ролей).

**Преимущества доказаны 22.05.2026:**
- ✅ **2% недельного лимита** на ~16 часов работы (~120 KB документации + 5 LUS-коммитов + deploy)
- ✅ **Качество выше** — каждый бот в узком scope, не отвлекается; reviewer ловит то что я бы пропустил
- ✅ **Конструктивная критика** — бот может **отказаться** выполнять инструкцию если она неверная (см. §8.5 ниже про ESCALATION-6 как канонический пример)
- ✅ **Параллелизм** — Z-FIX-2 и Z-FIX-3 шли частично параллельно, дает x1.5 ускорение
- ✅ **Прерываемость** — boty можно остановить, продолжить после света (с safety-handover)

**Недостатки / когда НЕ подходит:**
- Мелкие изменения (<50 LOC, один файл) — оверхед бóльше выгоды
- Исследовательские задачи без чётких границ — нужно сначала через Claude-оркестратор + Илью оформить decisions/
- Urgent live debugging — слишком много раундов чтобы спасать живой инцидент

## 2. Архитектура — 4 бота в `localbot` tmux

```
┌──────────────────────────────────────────────────────────────────────┐
│  tmux session: localbot (на buka-home, headless OK)                  │
│                                                                      │
│  ┌──────────────────┬──────────────────┐                             │
│  │ pane 0.0         │ pane 0.1         │                             │
│  │ NVR writer       │ LUS writer       │                             │
│  │ (доменный фокус) │ (доменный фокус) │                             │
│  └──────────────────┼──────────────────┤                             │
│  │ pane 0.2         │ pane 0.3         │                             │
│  │ Ultra Reviewer   │ Dispatcher       │ ← главный собеседник        │
│  │ (только ревью)   │ (брифует 0.0/1,  │   Claude-оркестратора       │
│  │                  │  забирает диффы, │                             │
│  │                  │  эскалирует)     │                             │
│  └──────────────────┴──────────────────┘                             │
│                                                                      │
│  Все 4 бота: claude --model claude-opus-4-7                          │
│              --dangerously-skip-permissions                          │
└──────────────────────────────────────────────────────────────────────┘
```

**Почему 4, а не 2-3 или 5+:**
- **2 бота** (writer + reviewer) — не хватает диспетчера, оркестратор сам формирует все брифы → ботлнек на оркестраторе
- **3 бота** (writer + reviewer + dispatcher) — работает, но writer-ы простаивают между задачами. Когда есть параллелизуемые задачи (Z-FIX-2 + Z-FIX-3) — теряем время
- **4 бота** (2 writer + reviewer + dispatcher) — **золотая точка**. Доказано
- **5+ ботов** — оверхед координации; dispatcher не успевает следить за 3+ writers

**Доменное разделение writers (0.0 vs 0.1):**
- Не строгое — в hot-fix цикле 22.05 оба фикса делал бот 0.1 (LUS scope), 0.0 простаивал
- **Полезно когда:** одновременно идут изменения в NVR и LUS репозиториях (не сегодняшний случай)
- **Альтернативно:** оба пишут в один scope последовательно (как было сегодня) — тоже OK

**Ultra Reviewer (бот 0.2) — read-only:**
- Никогда не коммитит сам, только проверяет
- Каждый коммит получает вердикт: 🟢 GREEN (merge OK) / 🟡 YELLOW (есть followup, не блокер) / 🔴 RED (блокер)
- Использует node --check, git show, читает диффы построчно
- **Не запускает код** — статический анализ + понимание контракта

**Dispatcher (бот 0.3) — главный мозг цикла:**
- Получает dispatcher-брифы от Claude-оркестратора
- Делает discovery (читает репо, БД, decisions/)
- Формирует брифы для writers
- Забирает диффы у writers, отправляет на ревью 0.2
- При неоднозначностях — эскалирует через `coord/escalations.md`
- Ведёт `coord/dispatcher-log.md` (хронология решений)
- **Никогда** не делает push в main / не деплоит в production

## 3. Запуск с нуля

### 3.1. Tmux session

На buka-home выполнить (один раз за сессию):

```bash
# если localbot уже жив — attach
tmux ls | grep -q '^localbot:' && xterm -e 'tmux attach -t localbot' &

# если нет — создать 4 panes
tmux new-session -d -s localbot
tmux split-window -h -t localbot
tmux split-window -v -t localbot:0.0
tmux split-window -v -t localbot:0.1
# теперь panes: 0.0 (top-left), 0.1 (top-right), 0.2 (bot-left), 0.3 (bot-right)
# запустить Claude Code в каждом
for p in 0.0 0.1 0.2 0.3; do
  tmux send-keys -t localbot:$p 'claude --model claude-opus-4-7 --dangerously-skip-permissions' Enter
done
# открыть xterm для визуального наблюдения Ильи
xterm -e 'tmux attach -t localbot' &
```

### 3.2. Стартовые промпты для ботов

После того как Claude Code загрузился в каждом pane, отправить **role prompt**:

**Бот 0.0 / 0.1 (writers):**
```
Ты — code writer в автономном цикле. Получаешь брифы от dispatcher бота 0.3.
Правила:
- Делаешь ровно то что в брифе, не больше
- Один коммит на одну задачу
- НЕ делаешь git push (это делает Claude-оркестратор позже)
- НЕ правишь modules/*.md (P-M-B принцип)
- Если в брифе противоречие или нет чего-то — СТОП и эскалируй через бота 0.3
- После коммита — git show --stat HEAD + git rev-parse HEAD, жди ревью
```

**Бот 0.2 (Ultra Reviewer):**
```
Ты — Ultra Reviewer. Read-only режим.
Правила:
- Получаешь от бота 0.3 коммит на ревью
- Проверяешь: дифф построчно, node --check / синтаксис, контракты API, влияние на существующие фичи
- Вердикт: 🟢 GREEN / 🟡 YELLOW + followup / 🔴 RED + блокер
- Можешь сверить с decisions/, modules/ — для понимания контекста
- НЕ коммитишь сам. НЕ запускаешь код в проде.
- После вердикта — СТОП, жди следующий бриф от 0.3
```

**Бот 0.3 (Dispatcher) — самый длинный role prompt, см. §6 ниже про формат брифа.**

### 3.3. Sanity check после запуска

В каждом pane убедиться что:
1. Claude Code загрузился, видна строка с моделью
2. `cd ~/nvr-cloud-2206 && git status` отрабатывает без ошибок
3. У бота 0.3 — есть доступ к vault для чтения decisions/ и записи coord/

## 5. Артефакты координации (всё в `coord/`)

| Файл | Назначение | Кто пишет |
|---|---|---|
| `coord/escalations.md` | Открытые вопросы и решения по ним. Каждая эскалация — `## ESCALATION-N` с meta + body | Бот 0.3 пишет, Илья и Claude-оркестратор отвечают inline |
| `coord/dispatcher-log.md` | Хронологический журнал событий цикла («21:55 бот 0.1 закоммитил X», «22:05 ревью 🟢») | Только бот 0.3 |
| `coord/customer-data.md` (и подобные) | Справочные данные, нужные ботам (реквизиты, конфиги, креды) | Claude-оркестратор / Илья |
| `decisions/<feature>-decisions.md` | Архитектурные решения **ДО** старта цикла | Claude-оркестратор + Илья |
| `audits/<date>-<topic>.md` | Результаты UI-обходов, диагностики, замечания | Claude-оркестратор |
| `reports/<date>-<feature>.md` | Итог завершённого цикла | Claude-оркестратор |
| `handovers/HANDOVER-<date>.md` | Передача между сессиями | Claude-оркестратор |

**Принцип:** все артефакты в git vault (`teslatel-claude-vault.git`) → переживают перезагрузку buka-home, доступны с любой машины Ильи.

## 6. Формат dispatcher-брифа

Минимальная структура (доказана 22.05):

```markdown
🚨 DISPATCHER TASK — <короткое имя>

== КОНТЕКСТ ==

[1-3 параграфа: что произошло до, какое production state, какие decisions/ применяются]

== ЗАДАЧИ ==

== Z-X-1 — <название> ==
[Что нужно. Где код. Как тестировать.]

== Z-X-2 — <название> ==
[...]

== РАБОЧИЕ ГРАНИЦЫ ==

1. Ветка: feat/<name> создать от main
2. Один коммит на задачу
3. НЕ push в main и НЕ merge — оркестратор делает merge+deploy
4. modules/*.md НЕ ТРОГАТЬ (P-M-B)
5. На production НЕ выходить — все изменения в feat/* локально
6. migrations НЕ нужны (или: миграции в migrations/00XX_*.js нумерация продолжение)
7. v<следующая версия> НЕ начинать — после hotfix цикл закрывается

== ПОРЯДОК РАБОТЫ ==

1. Создать ветку feat/<name> от main
2. Z-X-1 → бот 0.1 → ревью 0.2 → 🟢
3. Z-X-2 → бот 0.1 → ревью 0.2 → 🟢
4. Запушить ветку на origin (или НЕ пушить, см. границу 3)
5. Эскалация Claude-оркестратору «hotfix готов»

[Параллелизация — если возможно: какие задачи можно параллельно делать]

== ESCALATION POINTS ==

Эскалируй через coord/escalations.md (ESCALATION-N) если:
- [конкретные сценарии где нужен ответ Ильи]
- [сценарии где нужно решение оркестратора]

[Контактные правила: «Илья отошёл, я на связи каждые 5-10 мин»]

== ИТОГ ==

[1-2 предложения: какой конечный результат ожидается после твоей работы]

— Claude-оркестратор, <дата> <время>
```

**Что НЕ должно быть в брифе:**
- Пошаговая инструкция написания кода (бот сам выберет реализацию)
- Догадки про неизвестные тебе вещи (лучше «проверь X, если Y — сделай Z»)
- Угрозы / излишние требования

**Что обязательно:**
- Production-state references (какие коммиты сейчас в main)
- Границы (что НЕ делать)
- Escalation triggers (когда остановиться и спросить)
- Время — чтобы бот понимал срочность

## 7. Технические команды для оркестратора

### 7.1. Отправить бриф боту

**ВАЖНО:** bash heredoc ломается на круглых скобках в кириллице. Использовать python:

```bash
python3 << 'PYEOF'
brief = '''
🚨 DISPATCHER TASK — ...
[полный текст брифа]
'''
with open('/tmp/brief-0.3-task.txt', 'w') as f:
    f.write(brief)
PYEOF

tmux send-keys -t localbot:0.3 C-u  # очистить input если что-то набрано
sleep 1
tmux load-buffer /tmp/brief-0.3-task.txt
tmux paste-buffer -t localbot:0.3
sleep 3
tmux send-keys -t localbot:0.3 Enter
sleep 1
tmux send-keys -t localbot:0.3 Enter  # 2-й Enter часто нужен из-за autocomplete
```

### 7.2. Прочитать что у бота

```bash
tmux capture-pane -p -t localbot:0.3 -S -25 | tail -20
```

**Shadow text** (серые «призраки» прошлых команд) — не команды Ильи, игнорировать.

### 7.3. Проверить state цикла

```bash
# git log на ветке которая в работе
cd ~/nvr-cloud-2206 && git log --oneline feat/<name> ^main

# открытые эскалации
grep '^## ESCALATION-' coord/escalations.md

# журнал
tail -15 coord/dispatcher-log.md
```

### 7.4. Безопасный push «на всякий случай»

Если приближается риск прерывания (гроза, низкий заряд) — **запушить ветку преждевременно**:

```bash
cd ~/nvr-cloud-2206 && git push origin feat/<name>
# даже если бот ещё не сигналил «готово к merge» — коммиты на GitHub защищены
```

Это нарушает «бот сам пушит» границу, но **безопасность важнее правил в чрезвычайных ситуациях**.

## 8. Типы эскалаций — паттерны (с примерами от 22.05.2026)

### 8.1. Тип A — запрос данных у Ильи

**Пример: ESCALATION-4** — нужны реквизиты MaMaison и ТЕСЛАТЕЛ для миграции backfill.

**Когда возникает:** бот обнаружил что для задачи нужны конкретные данные (ИНН, креды, конфиги) которые он не может узнать сам.

**Что делает бот:** пишет в `escalations.md` блок `Что нужно от Ильи: ...`, ставит работу на паузу для зависимой задачи, но **может продолжать параллельные** задачи.

**Что делает оркестратор:** передаёт вопрос Илье в Claude Desktop, получает ответ, записывает в escalations.md + `coord/<type>-data.md`, пинает бота.

### 8.2. Тип B — запрос approval на critical action

**Пример: ESCALATION-5** — деплой v0.3.0 на production LUS.

**Когда возникает:** бот готов сделать **необратимое** действие на production (deploy, миграция, ревокация).

**Что делает бот:** пишет полный план («1. backup, 2. ssh ..., 3. docker compose up, 4. smoke-test»), описывает rollback, ставит **полную паузу**.

**Что делает оркестратор:** обсуждает с Ильёй, получает явное «да/нет», описывает кто выполняет (бот / оркестратор / Илья).

**Правило 22.05:** **production deploy всегда делает Claude-оркестратор через DC bash**, не боты (даже если у них есть доступ).

### 8.3. Тип C — dispatcher принимает решение сам

**Пример: ESCALATION-2** — features_catalog 12 ключей (без smtp orphan) vs 13.

**Когда возникает:** в брифе противоречие, **техническое** решение которое не требует Ильи (нет политики, нет необратимости).

**Что делает бот:** принимает решение, **обязательно записывает в escalations.md** «решение dispatcher» с обоснованием + **veto-окно** (Илья может оспорить).

**Что делает оркестратор:** проверяет логику, либо одобряет, либо отменяет (тип D ниже).

### 8.4. Тип D — veto от Claude-оркестратора

**Пример: ESCALATION-3** — бот 0.1 пытался править `modules/license.md` в составе L-LM-A.

**Когда возникает:** бот делает что-то противоречащее принципам (P-M-B: боты не правят modules), даже если по своей логике это разумно.

**Что делает оркестратор:** пишет VETO в escalations.md, объясняет принцип, требует откат изменений, **обновляет CRITICAL_RULES** если правило раньше не было явным.

**22.05 урок:** Veto это не наказание бота — это «правило заранее не было явным, теперь явное, продолжай».

### 8.5. Тип E — конструктивная критика инструкции (КАНОНИЧЕСКИЙ ПРИМЕР)

**Пример: ESCALATION-6** — Z-FIX-1 «features state bug». Я ошибся с диагнозом (проверял Alpine state по несуществующему пути `issueForm.features` вместо `form.features`). Бот 0.3 прочитал код, **отказался** выполнять, написал ESCALATION с фактологией:

> «В коде state называется `form`, не `issueForm`. Чекбоксы привязаны через `:checked`+`@change`. Submit передаёт `body.features`. Инструкция «передавать features_override» сломает рабочий контракт.»

**Что делает бот:** прежде чем выполнить инструкцию которая «странно выглядит» — **проверяет факты**, и если инструкция неверна, **отказывается выполнять** с конкретными ссылками на код.

**Что делает оркестратор:** ❗ **проверяет через инструменты** (playwright/grep/bash), и если бот прав — **признаёт ошибку**, отменяет инструкцию. Это §2.5 CRITICAL_RULES в действии.

**Это самый ценный паттерн.** Бот спас от breaking change в рабочем контракте. Поощряй этот паттерн в брифах: «если инструкция кажется неверной — СТОП и эскалируй, не выполняй слепо».

### 8.6. Тип F — discovery находка

**Пример: ESCALATION-1** — бот 0.3 при kickoff обнаружил что L-A1 «транзакция миграций» уже сделан в коммите `d4a443f`, я считал что не сделан.

**Когда возникает:** бот при discovery находит что часть задач уже выполнена / уже есть, либо что план базируется на устаревшем понимании реальности.

**Что делает бот:** пишет ESCALATION с **фактическими** ссылками (commit hash, файл:строка), предлагает пересмотр плана.

**Что делает оркестратор:** обновляет план в `decisions/`, обновляет modules если нужно ([[NVR-2026/LESSONS/2026-05-22-MODULES-AS-SOURCE-OF-TRUTH]]).

## 9. Обсуждение решений: Илья ↔ Claude-оркестратор ↔ боты

### 9.1. Тройка ролей

| Кто | Что делает | Что НЕ делает |
|---|---|---|
| **Илья** (человек) | Высокоуровневая цель, бизнес-приоритеты, approval critical actions, реквизиты | Не пишет код, не диктует синтаксис |
| **Claude-оркестратор** (Claude Desktop) | Дизайн, варианты A/B/C, decisions/, брифы, merge+deploy, modules/ | Не пишет код, не правит modules/ от имени бота |
| **Боты Claude Code** | Кодинг, ревью, discovery, dispatching | Не делают push, не правят modules/, не запускают next-version, не делают production-deploy |

### 9.2. Поток обсуждения решения (на примере L-LM-G)

```
1. Илья: «Нужны заказчики в LUS — для 1С интеграции, ИНН обязателен»
   ↓
2. Claude-оркестратор предлагает:
   - вариант A: один customer ↔ много licenses (1:N), customer_id FK на licenses
   - вариант B: customer ↔ license (1:1), убрать client_name из licenses
   - вариант C: гибрид — customer optional, client_name остаётся как display
   ↓
3. Илья: «вариант A — у нас будет один customer с несколькими лицензиями
        (наш ТЕСЛАТЕЛ: Core+DEV2+AI), а client_name оставляем для UI»
   ↓
4. Claude-оркестратор фиксирует в decisions/v0.3.0-decisions.md:
   - L-LM-G: customers table + licenses.customer_id FK + LEFT JOIN в endpoints
   - Поле customer_id NULLABLE (для лицензий без юр.лица)
   ↓
5. Запуск автономного цикла: бот 0.3 получает бриф с reference на decisions/
   ↓
6. Бот 0.3 при дискавери: «реквизиты конкретных заказчиков?» → ESCALATION-4 (Тип A)
   ↓
7. Claude-оркестратор передаёт Илье, получает ответ, записывает в customer-data.md
   ↓
8. Бот 0.1 пишет миграцию + endpoint + UI таб, ревью 0.2, всё 🟢
   ↓
9. Илья визуально проверяет → находит что customer-selector в форме issue ОТСУТСТВУЕТ
   ↓
10. Claude-оркестратор признаёт scope-провал → запуск hotfix-цикла Z-FIX-2 + Z-FIX-3
```

**Урок (записан в [[NVR-2026/REPORTS/2026-05-22]]):** разделение «backend» и «UI integration» на v0.3.0 и v0.3.1 было искусственным. С точки зрения пользователя фича работает только end-to-end. **Делай end-to-end в одном релизе**, даже если это удлиняет релизный цикл.

### 9.3. Когда Claude-оркестратор должен быть **громким**

Из [[CRITICAL-RULES#1.|§1]]: «**активно поднимает риски, альтернативы, возможности улучшения — не ждёт запроса**».

Конкретно:
- Видит scope-разрыв в decisions/ → говорит «я бы объединил X и Y» **до** того как Илья сам найдёт
- Видит что бот делает что-то неверное → останавливает **до** коммита
- Видит риск (электричество, гроза, потеря коммита) → **сразу** делает safety-action

## 11. Чеклист «перед запуском автономного цикла»

Перед первым `tmux send-keys` боту 0.3, оркестратор должен убедиться:

- [ ] **Decisions** написаны и Илья их одобрил (`decisions/<feature>-decisions.md` существует)
- [ ] **Production state** известен и записан в брифе (какие коммиты сейчас в main, какие миграции применены)
- [ ] **Pre-flight backup** сделан если задача затрагивает production БД (`/home/buka/.lus-disaster-recovery/...`)
- [ ] **CRITICAL_RULES** актуальны (если в этой сессии что-то новое — добавить в §7+)
- [ ] **Vault запушен** (без локальных изменений) — на случай прерывания
- [ ] **Боты живые** (`tmux ls` + `tmux capture-pane`) — каждый отвечает на промте
- [ ] **Илья на связи** или явно сказал «отойду на N минут, можешь автономно»

**Если что-то не выполнено** — НЕ запускать цикл. Сначала закрыть пробел.
