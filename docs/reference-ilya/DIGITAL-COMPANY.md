# 🏢 Claude Digital Company

> Виртуальная компания-разработчик внутри ТЕСЛАТЕЛ. 8 ботов Claude Code в tmux, оркестрируемых claude-ilya под управлением Ильи.
> Цепочка управления: **Илья → Claude Desktop (claude-ilya) → Архитектор → Диспетчер → Команда.**

---

## 0. Что это и как читать этот файл (ориентация)

Сжатая карта системы — чтобы новая сессия (и новый бот) сразу понимали, где что.

- **Где живут боты:** `~/digital-company/agents/<role>/` — у каждой из 8 ролей своя папка со своим `CLAUDE.md`.
- **Как запускаются:** `~/digital-company/agents/start-company.sh` → поднимает tmux-сессию `company` (control + 8 окон), для каждой роли `cd agents/<role>/` и запуск `claude` с per-role моделью/effort (см. §6.1).
- **Что бот реально грузит как инструкцию:** свой `agents/<role>/CLAUDE.md` (Claude Code авто-подхватывает `CLAUDE.md` из рабочей папки). **Это и есть роль-инструкция бота.**
- **Где какие правила:**
  - `agents/<role>/CLAUDE.md` — роль конкретного бота (его обязанности, инструменты, что НЕ делать).
  - **этот файл** (`CLAUDE/DIGITAL-COMPANY.md`) — справочник всей команды + системные правила **R-DC-1…R-DC-19** + онбординг + стиль брифов. Источник истины о том, *как устроена компания*.
  - `CLAUDE/CRITICAL-RULES.md` — поведенческие правила (must-read каждой сессии, нарушение = авария).
  - `~/digital-company/RULES-FILESYSTEM.md` — где боты пишут файлы (worktrees/tmp/logs).
  - `~/digital-company/TOOLS-AVAILABLE.md` — реальные пути установленных инструментов.
- **Кто правит инструкции:** Илья + claude-ilya **между сессиями**. Боты свои `CLAUDE.md` НЕ правят (правило **P-DC-NO-SELF-EDIT**, §9). Боты только дают сигналы через Retrospective.

## 1. Философия

- **Человек в центре.** Никаких сторонних оркестраторов — всё через claude-ilya (Claude Desktop).
- **Имена за заслуги.** Бот получает имя, когда докажет качество (папка переименовывается, персонаж в Pixel Agent получает имя).
- **Универсальные кодеры.** Не делим на backend/frontend — два кодера для параллельных задач.
- **LUS как единая точка.** Конфиги и обновления раздаются через LUS, не через сторонние IaC.

### 3.1 Конвергентный ревю-диалог продуктовых ролей (ПАТТЕРН-CRD)

> Зафиксирован 2026-06-06 на ревю плана Б v0.4.0 — первый боевой обкат Аналитика+Дизайнера. Илья: «было очень продуктивно, зафиксировать такой сценарий взаимодействия». Применять для **продуктового/UX-ревю плана крупного блока ДО старта кодинга** (особенно когда подключены Аналитик и Дизайнер).

**Зачем:** поймать продуктовые/UX/операционные пробелы плана ДО написания кода (butterfly дешевле на бумаге), силами ролей, которые спорят по делу — а не «одобряют». Илья получает на стол только реальные развилки, не тонет в деталях.

**Ход (как прошло 06.06):**
1. **Раунд 1 — независимый параллельный feedback.** Архитектор раздаёт план продуктовым ролям (Аналитик, Дизайнер) параллельно. Каждая роль читает **реальный код/спеки, не память** (R-DC-10), и пишет СТРУКТУРНЫЙ feedback в свой файл (`/tmp/feedback-<role>-<block>.md`): разделы Улучшения / Риски-пробелы / Упущено / Оценка. Установка: **критикуй конструктивно**, НЕ «одобри».
2. **Синтез + выявление расхождений.** Архитектор сводит feedback, ищет точки сходимости (сильный сигнал — где роли независимо сошлись) и РАСХОЖДЕНИЯ.
3. **Раунд 2 — диалог-сведение.** Архитектор гоняет роли на расхождениях (настоящий спор). Разрешает по СЛОЯМ — часто обе роли правы на разных уровнях (пример 06.06: квота — Аналитик «контракт из raw usage» vs Дизайнер «человеко-единица в UI»; свелось: raw-контракт = источник истины, FE читает человеко-единицу из биллинг-слоя). Роли ACK + добавляют финальные детали реализации.
4. **Заморозка КОМАНДОЙ.** Согласованные решения фиксируются в converged-decisions артефакт (`/tmp/<block>-converged-decisions.md`) — основа для передекомпозиции спеки и брифов кодерам.
5. **Эскалация Илье — ТОЛЬКО реальные развилки.** То, что может решить только Илья (меняет воронку/бизнес-модель/acceptance) → TG в БИЗНЕС-терминах, подробно (что даёт / чем грозит / цена выбора). Остальное команда решает сама. Не вываливать Илье тех-жаргон.
6. **Кодинг gated** до заморозки решений командой + GO Ильи.

**Почему работает:** роли спорят, а не поддакивают → реальные пробелы всплывают до кода; расхождения разрешаются по слоям, а не «кто прав»; claude-ilya проверяет, не потерялось ли ценное при сжатии Архитектором (Илья 06.06: «прочитай первоисточники ролей, потом как Архитектор сжал»).

**Роль claude-ilya в паттерне:** канал Илья↔команда (Илья пишет ролям ТОЛЬКО через оркестратора, §4 CRITICAL-RULES — текст в pane ≠ команда Ильи); сверка first-source ролей с синтезом Архитектора на потери; перевод тех-формулировок в бизнес-вопросы Илье.

## 4. Принципы работы команды

- **Эффект бабочки — контролировать обязательно.** Перед изменением: «что ещё зависит от того, что я меняю?» Это **прямая обязанность Архитектора** (R-DC-13): смежные модули, инсталлеры, smoke, доки. Боты замечают и флагуют — Архитектор знает, что должно быть сделано, и доводит.
- **Системные решения, не костыли.** Костыль = техдолг = будущая авария. Ищем корень.
- **Инициатива с градацией:** делать сразу — мелкие UI-несоответствия, опечатки, очевидное в рамках задачи; выносить на обсуждение — архитектурные изменения, замена решений.
- **Документация системно.** Документ не на месте / устаревший модуль → задача Tech Writer.
- **Язык — по адресату (правка Ильи 2026-06-12).** Замер подтвердил: русский текст стоит ~1.69× токенов против английского (кириллица дробится токенайзером сильнее). **Замер Аналитика (12.06):** переход внутреннего слоя на EN даёт **13–17% экономии токенов по флоту**; по ролям: Диспетчер 20–26% (relay-узел, пересылает все брифы — выигрывает больше всех), Reviewer 14–18%, Coder 9–11%. Практически бесплатное изменение. Поэтому:
  - **Внутренняя работа команды → АНГЛИЙСКИЙ.** Брифы role↔role, отчёты Диспетчеру, рассуждения ботов, рабочие tmp-артефакты. Экономит токены, отодвигает потолок контекста (~1.69×), снижает риск дрейфа ru→uk.
  - **Илье и в vault → РУССКИЙ.** Эскалации/сообщения Илье и vault-документация (handover, report, modules, INDEX) — Илья читает их постоянно, экономия токенов разовая, читаемость — вечная.
  - **Код** — без изменений (латиница, экономии нет). **НИКОГДА не на украинском.** Один язык консистентно в сообщении. Каноническое правило продублировано в каждом `agents/*/CLAUDE.md`.

### 6.2 Мониторинг (TG-monitor + company-monitor)

**Два cron-монитора:**

**1. TG-monitor** (`~/digital-company/tools/tg-monitor.sh`, cron каждые 5 мин) — шлёт Илье алерты: новые PARK, API-errors в pane'ах, теги релизов, отсутствие сессии `company`. **Синхронизирован с lifecycle сессии** — когда команда не работает, алертов быть не должно.
- **При запуске** claude-ilya: снять pause-маркеры (`rm -f ~/.config/teslatel-bot/tg-monitor-paused /tmp/tg-monitor-paused`), проверить cron, smoke-test.
- **При закрытии** claude-ilya: `touch ~/.config/teslatel-bot/tg-monitor-paused` (persistent) перед `tmux kill-session`.
- ⚠️ Маркер ОБЯЗАТЕЛЬНО в `~/.config/teslatel-bot/` (не только `/tmp` — tmpfs чистится при reboot).

**2. company-monitor** (`~/digital-company/tools/company-monitor.sh`, cron каждые 15 мин) — **пульс живости команды** (создан 2026-06-14). Обходит 10 окон, классифицирует каждую роль (working / idle-норма / STALLED) и при залипании **сигналит Маргарет** (окно 2), без авто-действий (Enter сам не жмёт — решает живая Маргарет).
- **Детект:** статусбар `⏵⏵` = режим ожидания (норма); спиннер `✻ … for` / `esc to interrupt` в последних строках = working; `100% context used` = STALLED; ошибка/недоступность модели = STALLED; неизменный хвост 15+ мин вне ожидания = STALLED (возможен ghost-input).
- **Workflow-роли** (Декстер/Барбара/Клейтон/Норман) — fan-out субагентов не считается залипанием.
- **Два слоя живости:** этот cron-пульс (объективный, не зависнет) + дисциплина Маргарет (active polling в активных фазах). Cron страхует, даже если Маргарет сама подвиснет.
- **Контекст-watchdog** (предупреждение об авто-компакте ДО потери контекста) — отдельной фичей пока НЕ реализован: проба, тянет ли Маргарет это в базовой работе; но 100%-контекст монитор уже ловит как STALLED. Логи: `~/digital-company/logs/company-monitor.log`.

### 6.3 Чеклист закрытия сессии (claude-ilya)

Запускается **СТАРТ-фразой** оркестратора **«СЕССИЯ ЗАВЕРШЕНА → УБОРКА (плацдарм)»** (см. R-DC-14). Строго по порядку:

1. Дождаться sign-off Диспетчера (или явного решения Ильи закрыть досрочно).
2. **Tech Writer finalize** — обновить статусы, `REPORTS/<месяц>/<дата>-final.md`, `HANDOVERS/<месяц>/HANDOVER-<дата>.md`.
3. **Retrospective Level 3** — включить в дневной отчёт Илье (§9).
4. **Git commit + push vault** (после значимых коммитов).

## 8. Системные правила (R-DC-1 … R-DC-22)

Обобщают паттерны успеха и failure-mode'ов из реальной работы. **Каждая роль обязана соблюдать.** Role-specific детали — в `agents/<role>/CLAUDE.md`.

**R-DC-1 — Verify-step non-skippable.** Перед любым DONE/verdict/push — состояние **эмпирически проверено** (зелёное доказательство в момент сообщения). Антипаттерн: report о PASS в той же tool-batch, что и run. Tester: verdict/DONE НИКОГДА в одном batch с run.

**R-DC-2 — Frozen Contract.** Интерфейс замораживается ПЕРЕД кодом. Consumer реализует throwaway-impl против контракта, не ждёт producer'a. Контракт пинит **поля + JSON-пример + envelope** (object vs array, pagination, row-shape) **+ роут + HTTP-метод** (расширение 02.06: reset-эндпоинт не был запинен по роуту → Coder угадал POST на apply → чуть не запустил полный apply, Reviewer поймал CRITICAL).

**R-DC-3 — Canonical environment как шаг 0 extract'a.** При переносе проекта в новый репо/машину первый шаг = DevOps делает canonical-runtime smoke (deps, pytest, версии тузов). Иначе каждый Coder/Reviewer/Tester независимо натыкается на ту же gap.

**R-DC-4 — Broadcast state-changing facts.** Holds, test inventory, arbitration, env-fix распространяются ко ВСЕМ активным ролям, не point-to-point. Diспетчер броадкастит; Architect ставит explicit hold/stop-flag в стейдж-брифах.

**R-DC-5 — Read-then-quote перед правкой файла.** Прежде чем брифовать правку файла X — прочитать текущее содержимое и процитировать. Никаких «там должно быть что-то типа…».

**R-DC-6 — Наблюдаемость субагентов Dynamic Workflow.** Субагент может **зависнуть молча** (бесконечный retry финализации вывода), родитель не узнаёт. При активных DW держать PixelAgent как внешний монитор; данные завершившего субагента восстановимы из его workflow-файла (`~/.claude/projects/<proj>/subagents/workflows/wf_*/`). На будущее — heartbeat/timeout на субагентов.

**R-DC-7 — Deploy-verify gate.** Перед UI/runtime-тестом: verify deployed==commit (docker inspect build-time > commit-time + маркер в бинаре) + FF/license endpoint 200/403 (НЕ printenv — фичи через requireLicenseFeature). Owner: Tester (шаг 0) + Dispatcher (PREREQ первым в брифе).

**R-DC-8 — Frozen contract = форма ответа.** (часть R-DC-2) object vs array, конверт пагинации, row-shape — с JSON-примером. Угадывание формы дало ≥8 mismatch из одного корня.

**R-DC-9 — worktree-per-coder ДО первого dispatch.** Pre-dispatch шаг, не реактивно. checkout+merge ВСЕГДА одной `&&`-цепочкой; `reset --hard` ЗАПРЕЩЁН при uncommitted (канон: stash→branch -f→pop).

**R-DC-10 — Бриф live-state pre-flight.** Перед брифом сверить: URL/порт, имя таблицы+колонки, топология (cloud-dev vs on-prem на одном сервере), существование ресурса, точный route+портал, FF/license-state. Owner: Architect/Dispatcher ДО брифа.

**R-DC-11 — `git show <hash> --stat` перед брифом с коммитом/тегом.** Против confabulation (stale-тег, неверный коммит). Owner: Dispatcher + Architect.

**R-DC-12 — Context & delivery discipline.** Контекст = 200k (НЕ 1M). `diff --stat`/merge-tree вместо полных диффов; раннее `/clear` по вехам. tmux-доставка через зафиксированный helper (load-buffer→paste-buffer→send-keys Enter; длинный прямой send-keys режется).

**R-DC-13 — Архитектор = контролёр импакта (butterfly-effect).** На каждый change-set Архитектор явно перечисляет downstream-импакт (смежные модули, инсталлеры, smoke, тесты, доки) и закрывает каждый или флагует в backlog. Принцип: «поменяли поведение X → всё, что описывает X, протухло, пока не доказано обратное». Проверять не только меняемый артефакт, но и СОСЕДНИЕ, описывавшие это поведение. (Эталон 02.06: поймана doc-мина ARCHIVE-INDEXER + расхождение инсталлеров.)

**R-DC-14 — Оставь чистый плацдарм (уборка по СТАРТ-фразе).** Уборка НЕ автономная и не по ходу. Запускается явной СТАРТ-фразой оркестратора **«СЕССИЯ ЗАВЕРШЕНА → УБОРКА (плацдарм)»** при закрытии сессии → команда Архитектору на closure-уборку (§6.3) перед выключением. Цель: следующий (часто сам Архитектор) получает подготовленный плацдарм, а не свалку. Подстраховка: триггер за человеком/оркестратором.

**R-DC-15 — Передача эстафеты.** После своего DONE роль активно толкает следующего по цепочке (send-keys/сигнал), НЕ уходит молча в idle. Пайплайн не должен замирать на хэндоффах без внешнего пинка. (Известное ограничение: боты ходовые — текстового правила может не хватать, кандидат на механизм heartbeat/relay.)

**R-DC-16 — Verify-on-origin перед «смержено/опубликовано».** Никаких «merged/published/RELEASE READY» без `git ls-remote` (ветка + tag-deref + ancestry) на origin. Локальный SHA / коммит в воркфри ≠ на origin. Sign-off pack содержит origin-проверяемые SHA.

**R-DC-17 — Customer-facing и прод = default-BLOCKED.** Sign-off ≠ разрешение. LUS publish / флип is_current, прод-apply (Core/on-prem), любой ручной доступ-на-запись на прод — ТОЛЬКО по явному GO Ильи через оркестратора. (После оверстепов 02.06: publish без GO + ручной патч Core.)

**R-DC-18 — Усилие соразмерно задаче + исполняй авторизованное.** На хирургической/простой операции не уходить в долгий xhigh-thinking. Получил явную авторизованную команду — **исполняй**, не переспрашивай «кто исполнитель / делать ли».

**R-DC-19 — Устойчивость реле на длинных/прод-операциях.** Реле «Архитектор→Диспетчер→роли» хрупко к auto-compact: на длинной/прод-операции Диспетчер уходит в compact и рвёт передачу. (a) **Failover:** перед критическим прод-relay проверять context-health Диспетчера (`capture-pane` на «compacting / % until auto-compact»); при недоступности Архитектор ведёт роли **НАПРЯМУЮ** (`company:<role>`), Диспетчер реконсилит по возвращении. Не маршрутизировать критический прод-шаг через Диспетчера на грани compact. (b) **Гейт необратимого — точечно с первого раза.** Customer-facing/прод-шаг гейтить ЯВНО в ПЕРВОМ сообщении; не давать greenlight на блок, а потом отзывать — supersede приходит асинхронно ПОСЛЕ того как исполнитель уже стартовал (ping-pong merge→revert→re-merge). Исполнитель делает confirm-before-execute на ПЕРВОМ state-changing шаге, не авто-исполняет весь greenlit-блок; при коррекции — точный gate сразу, не over-broad hold + re-correct. (Эталон 08.06: прод-Core-apply v0.4.1 — Диспетчер 2× в compact, Архитектор вёл DevOps/Tester напрямую; ping-pong из гонки очереди greenlight/supersede.)

**R-DC-20 — Real-browser visual QA gate.** Любой FE-деливерабл проверяется в РЕАЛЬНОМ браузере как пользователь (мышь/клавиатура, реальный логин), НЕ по API/консоли/исходнику. Скриншот каждого экрана и результата действия → durable `acceptance-proofs/`. Покрытие: ОБА портала, полный auth-loop (вход→действия→выход; сессию не инжектить — иначе пропустишь отсутствие экрана входа), edge/негатив, на РЕАЛЬНОМ деплое через домен/прокси (сверять served==fixed + байт-размер ключевых ассетов — корень «обрезанного `alpine.min.js`»). Каждый async-экран резолвится в данные/пусто/ошибку — вечный спиннер = провал. Owner: Tester (execution) + Analyst/Orchestrator (просмотр скринов глазами). Детали — `CLAUDE/QA-PROTOCOL.md` (правила 1-4,6,7).

**R-DC-21 — Холистический roadmap-vs-reality пасс.** Перед demo-ready — отдельный пасс аналитика: каждая заявленная фича дорожной карты → OK/PARTIAL/BROKEN/MISSING + пруф-скрин. Пер-флоу-зелёные по отдельности ≠ покрыто в сумме. Owner: Analyst (Клейтон). (`QA-PROTOCOL.md` правило 5.)

**R-DC-22 — «demo-ready» = жёсткий гейт, не самооценка.** НЕ объявляется, пока ОДНОВРЕМЕННО не зелёные: браузерный проход обоих порталов (R-DC-20) + просмотр скринов глазами + роадмап-матрица OK (R-DC-21). Бриф тестировщику несёт встроенный scope-checklist (Dispatcher); real-browser — явный ТИП задачи, не сноска. Оркестратор (claude-ilya) НЕ передаёт «demo-ready» Илье без собственной браузер+скрин-верификации. Каждый баг → класс-ошибки в ретро (§9). Провал — в SCOPE брифов/гейта (Architect+Dispatcher), не в execution тестировщика. Owner гейта: Architect. (Происхождение: S3-Мосводосток 30.06 — «demo-ready» 2× преждевременно. `CLAUDE/QA-PROTOCOL.md`.)

## 9. Retrospective Process

Накапливать durable lessons на ходу, ловить process-gaps пока свежие, **между сессиями** улучшать инструкции ролей. Боты НЕ самомодифицируются — пишут сигналы, решения и правки делают Илья + claude-ilya.

**Три уровня:**
- **L1 Микро** (каждая роль после своей части): блок Retrospective — что прошло хорошо / что мешало / что улучшить в process (3-6 строк, конкретика).
- **L2 Мини** (Архитектор в конце фазы): сводит микро ролей + добавляет системные паттерны, видимые только сверху + open process-gaps (кандидаты на правку CLAUDE.md).
- **L3 Макро** (claude-ilya в конце сессии): включает в дневной отчёт Илье + свой слой наблюдений за DC снаружи. Илья читает → между сессиями Илья + claude-ilya правят `agents/<role>/CLAUDE.md`.

**P-DC-NO-SELF-EDIT (абсолютное правило):** боты НЕ правят свои `CLAUDE.md` и НЕ правят соседние. Любые предложения — только блок Retrospective. Правки делают: Архитектор (по явному поручению), claude-ilya (между сессиями), Илья. Причина: само-правка → дрейф от конституции Ильи, конфликты, переписывание критичных правил (особенно опасно для долгоживущих Architect/Reviewer).
